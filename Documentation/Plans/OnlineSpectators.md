# Online spectator implementation plan

Let invited viewers follow a Counterattack session from the lobby through setup, Draft, Room and the final result while the two managers keep control of their teams. Build on the existing guest rendering path and keep the spectator lifecycle independent of online save and resume.

## Player and viewer flow

1. The host shares one **Match Code** for the session. Use eight hexadecimal characters (0–9 and A–F), accept either case, and keep leading zeros. Provide **Copy Match Code** in the host lobby and make it available during the match through permanent Room UI. Choose its exact in-match placement when authoring the permanent controls, independently of temporary online panels. Copying the code leaves the match clock running. **Allow spectators** defaults to on. Show both managers whether viewing is enabled and how many viewers are connected. Let the host turn viewing off before or during the match.
2. Guests use **Online → Join** and enter the Match Code. After validation, show **Join as Away** while a new match's Away seat is free and **Spectate** while viewing is enabled and there is capacity. The host grants the first valid Away request atomically. Both manager seats must be assigned before setup advances. Spectators follow the current stage as viewers, starting in the lobby if they join before both managers are assigned. They follow the shared progression through Create New Game and Draft before entering Room with the initial match state. Later viewers use the same code and join the current stage. Show clear feedback for invalid or closed sessions, full capacity, incompatible builds, and connection failures.
3. In Room, sync the pitch, lineups, ball, teams and crowd colors, score, scorers, stats, clock, shared pause panel, coin tosses, dice rolls, public events and final result. Spectators control their own camera, use a white pointer to hover over public information, and can press **Space** to preview player cards. They can hide and reopen Match Stats and open Rules through the in-game button. These controls are local to the viewer. Provide **Leave** through the authored menu.
4. Start with a cap of **two spectators** in addition to the two managers. Treat the cap as a release setting to validate on paired builds. Keep the first release focused on live, code-based viewing. Public discovery, chat, replays, delayed broadcasts and seat takeover are future work.

## 1. Admit viewers without taking a player seat

- Keep the current two-seat manager lobby. Prototype a separate EOS watch lobby owned by the same host, with presence disabled and its own internal lobby ID, socket or channel, capacity and lifecycle. Resolve the shared Match Code even when the EOS manager lobby is full. Continue implementation while the three-device test is pending. Verify simultaneous lobby ownership, late joins and cleanup with packaged Windows and macOS clients before release. If the deployment cannot support the separate lobby, resolve the transport design before release. [EOS lobby permissions](https://dev.epicgames.com/docs/epic-online-services/multiplayer/lobbies-and-sessions/lobby-interface/lobby-interface-reference)
- Treat lookup and role authorization as separate steps. The host's game automatically verifies the EOS identity, Match Code, compatibility and capacity before granting the requested role. Generate the eight hexadecimal characters with a cryptographic random source, publish the lookup value, and verify the full code during the handshake. Evaluate code guessing and lobby occupancy abuse before release. Bind each admission to the authenticated peer, current match and role. Once Away is assigned, reserve it for that manager on reconnect. Rate-limit admission, expire pending requests and reject duplicate, stale and excess requests. Only approved viewers receive public match state or occupy a viewer seat. Verify that unapproved EOS members cannot keep valid guests out before enabling viewing by default. Turning viewing off disconnects viewers and disables new viewer admission. The Match Code stays valid for manager reconnect until the session ends.
- When save/resume is available, keep the original authenticated Home and Away identities reserved. A different guest can use the same Match Code to spectate if viewing is enabled. Only the original Away manager can use the manager role. Viewers follow the resumed session's actual stages, including its waiting and ready states.
- Preserve the manager connection and its recovery flow. Introduce an independent spectator connection table and dispatch using the authenticated sender and channel. Reject every gameplay or shared-control request from viewers, including pause, rolls, substitutions, readiness and saves, before it reaches the gameplay command handler. Viewer join, acknowledgement, disconnect or retry cannot hold or resume match play. Start from [OnlineFrontendSession.cs](../../Assets/Scripts/Online/OnlineFrontendSession.cs), [OnlineMatchProtocol.cs](../../Assets/Scripts/Online/OnlineMatchProtocol.cs) and [EOSStandalonePacketProbe.cs](../../Assets/Scripts/Online/EOSStandaloneProof/EOSStandalonePacketProbe.cs).

## 2. Render the public view at each stage

- Add the role chooser to the existing Online submenu as an authored player-card-style panel, with the available roles as menu items. Reuse the submenu's typography, colors, selection states and back navigation.
- Add an explicit spectator role with no local team. Publish the current shared stage and render its read-only state in the lobby, Create New Game, Draft and Room. Follow shared transitions as the managers reach them. Bootstrap the Room board, tokens, kits, ball and crowd colors from the first complete Room publication after setup and Draft are finished. Viewer loading, readiness, and scene changes never gate either manager.
- Reuse replica rendering in Room. Audit `IsGuest` and team assumptions before sharing code. Show and hide the shared pause panel in sync with the managers, with gameplay and shared pause controls unavailable to spectators. Preserve local camera and Rules access, including while the match is paused. Limit the white spectator pointer over the pitch to hovering and opening public previews. Route **Space** only to the player-card preview in spectator mode. Hide or reopen the authored Match Stats panel locally and keep its data current while hidden. Never send pointer position, hover, preview, Rules, or Match Stats visibility over the network. Spectator bootstrapping must avoid authority initialization, gameplay input, manager prompts and match-save writes. Author status and spectator menu controls in scenes or prefabs. [OnlineRoomSession.cs](../../Assets/Scripts/Online/OnlineRoomSession.cs) · [OnlineRoomStartup.cs](../../Assets/Scripts/Online/OnlineRoomStartup.cs) · [OnlineGroundPassBoard.cs](../../Assets/Scripts/Online/OnlineGroundPassBoard.cs)
- Build a spectator publication with an explicit list of public fields for each stage. Include shared setup settings, revealed Draft picks, committed positions and animations, visible roster and kit data, score and scorers, match stats, clock, shared pause state, public coin toss and dice roll animations and results, public announcements and final result. Reveal results when they become visible to both managers. Spectators cannot trigger, acknowledge or dismiss shared rolls. Exclude legal actions, uncommitted movement and target previews, cursors, private setup and Draft selections, and account or save metadata. Audit nested pose and event data as well as top-level fields.
- Send late joiners a complete public snapshot of the current stage, then ordered stage transitions and updates using the match identity and publication sequence. Viewer recovery requests a fresh snapshot and drops obsolete updates without affecting managers. Use separate bounded queues and rate limits, replace superseded snapshots for slow viewers, and prioritize manager traffic. When the host shuts down, show a clear end-of-session state and release both lobby and transport resources.
- Apply the compatibility rules in [CONTRIBUTING.md](../../CONTRIBUTING.md). Version the spectator handshake and publication. If the implementation also changes required manager messages, bump the affected protocol and verify existing two-player sessions with spectators disabled. Keep spectator work independent of any future saved-match loading.

## Verification checklist

- [ ] Qualify simultaneous EOS lobby ownership and late viewing with the [standalone transport proof](../Setup/EOSStandaloneProof.md#spectator-lobby-transport-proof).

- [ ] Add dedicated `OnlineSpectators` feature tests and a short checklist. EditMode cases cover Match Code validation before and after Away is filled, simultaneous Away claims, full and duplicate admission, identity/role isolation, stale messages, and exclusion of private fields from encoded snapshots. Verify that spectators cannot claim or hold a manager seat. Send disallowed commands through the actual host dispatch path and assert they have no match effects.
- [ ] PlayMode cases cover both manager seats gating setup, read-only spectator progression from the lobby through Create New Game and Draft, late joins during Draft and Room with the original code, and Room bootstrap with correct ball, tokens, kits and crowd colors. Verify synchronized score, scorers, stats, clock, shared pause panel and final result. Cover local camera, white pointer, public previews and Rules access during pause. Check that spectator pointers are absent from both manager screens and that spectator input cannot affect gameplay or pause state. Verify that copying the Match Code, viewer disconnection, resync and repeated joins leave manager progression and timers intact. Preserve the two-manager flow with viewing disabled.
- [ ] Verify coin toss and dice roll animations and results are visible to the spectator at the public reveal, without spectator input or acknowledgements. Verify **Space** previews player cards without sending a gameplay action, and that hiding and reopening Match Stats is local and shows current values.
- [ ] Run the focused Unity tests under [AGENTS.md](../../AGENTS.md). Record compilation separately from passed, failed and skipped counts. Retain native XML and progress under `TestResults/GameplayRegression/Runs/`.
- [ ] Run packaged Windows and macOS clients with two managers and one viewer, then repeat at the spectator cap. Exercise cross-network joins, direct and relay paths where available, a slow viewer, disconnect and rejoin, and clean shutdown. Compare manager command latency, host frame time and outbound traffic with zero viewers and at the cap. Base any cap increase on those measurements.
